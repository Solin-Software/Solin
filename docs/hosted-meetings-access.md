# Hosted meetings: links, access, schedule and attendance

Specification agreed on 2026-11-17. It changes how people reach a meeting that Solin hosts itself (see [hosted-meetings.md](hosted-meetings.md)), and it touches both Solin and the hub ([solin-hub](https://github.com/Solin-Software/solin-hub)).

**Status:** implemented on `spike/galene` and in solin-hub (see "Implementation status" at the end). The hub creates the codes, each owned by a secret only the Solin that asked for it holds, and routes `meet.solin.run/<code>` to that Solin's tunnel. Solin still checks the password itself.

The hub is at `meet.solin.run`.

## Goals

- **Short links:** a link short enough to read aloud: `meet.solin.run/k7m4p2`. No long addresses anywhere, not even behind a redirect.
- **One password:** for every page.
- **The lobby still decides:** the operator, or a remote moderator, admits each attendee.
- **Recurring meetings:** either one link for every meeting, or a new link for each meeting, prepared weeks ahead.
- **Attendance:** counted once per device, and taken at the moment the instructions require.

## Pages

| Address | Page | Who |
|---|---|---|
| `meet.solin.run/<code>` | Attendee | Everyone with the link and password |
| `meet.solin.run/<code>/s` | Stage | The device on the platform: participants and raised hands, read-only |
| `meet.solin.run/<code>/m` | Moderator | Remote moderators, approved by the operator |

### Code

- **Format:** 6 characters from `23456789bcdfghjkmnpqrstvwxyz` (28 symbols, about 480 million codes).
- **Excluded characters:** `0 o 1 l i`, which are easy to confuse, and every vowel, so a code never spells a word.
- **Typing:** capitals, spaces and dashes are accepted and normalised. `K7M-4P2` works.
- **Issued by the hub:** it guarantees uniqueness across all congregations.
- **Never reused:** a retired or expired code is not handed out again for at least a year, so an old message never leads to another congregation's meeting.
- **Hidden name:** a code says nothing about the congregation.

### Password

- **One password per link,** for all three pages.
- **Generated by Solin:** 6 random digits. The operator may type their own instead.
- **Checked by the hub:** Solin uploads a **salted, slow hash** (scrypt), never the password itself. The hub can therefore answer "wrong password" even while Solin is closed.
- **Rate limits:** the hub limits failed attempts per IP address and per code.
- **Without a hub:** the hall checks the password itself.

## Attendee page

The first screen, shown right after the page loads and before anything else, asks for:
1. **Name.**
2. **Password.**
3. **"How many people are watching on this device, including you?"**
   - Buttons `1 · 2 · 3 · 4 · 5 · More…`, where "More…" opens a number field capped at 20.
   - Plus **Already counted**, which counts 0.
   - Nothing is pre-selected.

The browser remembers the name and the count for next time, pre-filled. The password is not remembered.

After a correct password, the page shows the state of the meeting. The address stays the same and the page switches between states on its own, with no reload:

| State | Served by | Shown |
|---|---|---|
| The operator has not opened the meeting yet (before or inside the window) | Hub | "The meeting starts at 19:30." A countdown ("40 minutes until the start"). A subtle tip: "The meeting operator hasn't opened the meeting yet. Please wait." |
| The operator has opened the meeting | Hub → hall | "The operator has opened the meeting. You'll be let in shortly." Then the lobby. |
| Admitted | Hall | The meeting, with a subtle countdown until the scheduled start. |
| Solin dropped during the meeting | Hall page | "Reconnecting to the meeting…". When Solin returns, people who were already admitted go straight back in, without the lobby. |
| The operator pressed **End meeting** | Hall, then hub | "This meeting has ended." Only an explicit end shows this, never a lost connection. |
| The window has closed and no meeting is running | Hub | "This meeting has ended." |
| A replaced or unknown code | Hub | "This link is no longer valid. Ask your congregation for the current link." It never redirects. |

**Clock.** Countdowns use the hub's time, not the phone's.

**Without a schedule.** For a meeting the operator starts outside the schedule, the waiting page says "Waiting for the operator" and shows no countdown.

### Count

- **Asked once, fixed:** the count is asked once and cannot be changed afterwards, by the attendee, the operator or a moderator.
- **Reconnecting:** a person who reconnects keeps their number.
- **Live in the lobby:** the lobby and participant lists show it next to the name ("Silva · 3"). These per-name numbers exist only while the meeting runs. Nothing is saved afterwards: no attendee list, no history.
- **Live total:** shown in the meeting panel all the time: "Online: 37 people on 21 devices".
- **Official count:** taken at **0.75 of the meeting's duration**. With the 2-hour worst case below, that is **1h30 after the scheduled start**.
  - Solin shows a notification with the number and a copy button, so it can be registered.
  - The moderator page shows the same notification.
  - The number stays visible in the meeting panel until the meeting ends.
  - Unscheduled meetings get no notification, only the live total.
- **Not counted:** stage devices, moderator devices and Solin are never asked and never counted.

## Stage page (`/s`)

- **Content:** the participants, raised hands in the order raised, and who has the floor, in large text. No audio, no video, no buttons. Someone on the platform who needs to moderate uses `/m`.
- **Access:** name and the meeting password, then the **operator's approval**. Afterwards the device is remembered, and it is not asked for the password or approval again.
- **No network check.** It is read-only, so it is not worth one.
- **The panel:** the device appears in Solin with a **Stage** badge.

## Moderator page (`/m`)

**Same power as the operator over people:**
- admit or refuse people in the lobby;
- remove someone;
- call someone to speak, and release them;
- mute or unmute anyone, and lower raised hands.

**Not allowed:** scenes, the program, ending the meeting, links and passwords. Those stay in Solin. When the operator and a moderator both act, the latest action wins, and every console updates live. A congregation can have several moderators.

**Joining:**
1. **Name and the meeting password.**
2. **The operator's approval is required.** The password is shared with everyone, so this approval is the real gate. The panel shows the request clearly apart from the lobby: "**Wants to be moderator**: Name".
3. **On approval, the browser creates a device key:** a non-extractable WebCrypto key pair (ECDSA P-256), kept in IndexedDB.
   - The hall stores only the public key.
   - On every later visit the page signs a fresh challenge from the hall, and that proves it is the same browser on the same device.
   - A copied cookie, link or password is useless on another device.
   - Clearing the browser data or using a private window means asking for approval again.
   - Passkeys are deliberately not used: Google and iCloud sync them between devices. Browser fingerprinting is not used either.
4. **Later visits** skip the password and the approval.

**Extras:**
- **Network change:** when an approved moderator reconnects from a different network than last time, the panel shows an informational note. It does not block.
- **Expiry:** approved moderator devices expire after a few months (proposed: 6).
- **Device list:** the panel lists every approved device (name, Moderator or Stage badge, last seen), each with a Remove button. Removal is immediate.
- **Belongs to the congregation:** an approved device belongs to the congregation, not to one code. In "a new link for each meeting" mode, it opens each meeting's new link and is still recognised.

**Badges:** Stage and Moderator badges appear in Solin, on `/m` and on `/s`. Attendees never see badges.

## Recurring meetings

Setting **Meeting links**, under Hosted meetings:
- **Same link for every meeting:** one code and password, with no expiry.
- **A new link for each meeting:** a code and password for each scheduled meeting.

Internally both use the same model: a link = code + password hash + optional window.

### Schedule

- **Generated by Solin:** from the congregation's midweek and weekend meetings, **4 weeks ahead**, topped up whenever Solin runs online.
- **Edits:** the operator can move a single meeting, cancel one, or add a one-off meeting.
- **Low-codes warning:** when fewer than **2 weeks** of codes remain, because Solin hasn't been online, Solin shows a warning. The hub never creates codes on its own.
- **Same-link mode:** Solin still sends the hub the next 4 weeks of start times, so the permanent link can show the countdown.
- **Meeting panel before a meeting:** the upcoming meetings with date, time, code and password, and copy or share buttons for each.
- **Share the month:** a ready-to-paste text for WhatsApp, one line per meeting with date, time, link and password.
- **Stage and moderator devices** use each meeting's new link as well. There is no permanent "home" code.

### Window

- **End time:** the worst-case duration is 2 hours. **Window = start − 30 min … start + 2 h + 30 min.** Example: a 19:30 meeting has the window 19:00–22:00.
- **Automatic start:** Solin opens the meeting automatically when it runs inside the window. If it is already running before the window, it opens the meeting when the window opens. Each time, Solin shows a notification ("Meeting opened automatically").
- **Open now:** an **Open now** button lets the operator open earlier than the window.
- **Late meetings:** the window never cuts a running meeting. After it closes, only new arrivals are turned away.
- **Choosing the meeting:** when the operator starts a meeting, Solin picks the scheduled meeting for now. Without one, it creates an unscheduled meeting.

## New link

New link is for a link or password that has leaked.

- **Replaces the code and the password.** The old code is retired, and the old address shows "no longer valid" without ever redirecting.
- **Removes every approved moderator and stage device,** automatically, every time.
- **Needs the hub,** which issues codes. When Solin is offline the button is disabled, with an explanation.
- **Only when no meeting is running.** While one is live, the action for the running meeting is disabled: "End the meeting to create a new link".
- **Asks for confirmation:** "Everyone will need the new link and password. Moderators and stage devices will need to be approved again." Afterwards Solin offers the share text.

**By mode:**
- **Same link for every meeting:** one **New link** button.
- **A new link for each meeting:**
  - **New link for this meeting** on each upcoming row. It is allowed for future meetings even while today's meeting runs.
  - **Renew all upcoming meetings,** which skips a meeting that is running, and is followed by **Share the month**.

**Changing only the password** is allowed. The code stays, and approved devices are kept, since they don't use the password any more.

## Ownership and routing

- **No registration.** The hub is open to every Solin. Settings → Integrations → Hosted meetings → **Meeting server** defaults to `meet.solin.run`; a congregation running its own hub types its address; empty means meetings on this network only. (Decided 2026-11-18: an open hub is acceptable, since the software is only useful for congregation meetings.)
- **The hub creates the codes.** Solin asks for a code with the sha256 of a fresh random **owner secret**, and keeps the secret. Whoever holds the secret owns the code: it sets the code's start time and state, opens the meeting's tunnel and gets TURN credentials for it. Each code has its own secret, so codes are not tied to a computer or a building; they move with the Solin profile.
- **Kingdom Halls shared by several congregations:** each congregation (Solin profile) has its own codes, schedule and devices.
- **Path routing on one host:** `meet.solin.run/<code>/…`, one TLS certificate.
  - Caddy asks the hub's service about each request: an open meeting goes through its tunnel; otherwise the hub answers itself (waiting page with countdown, "no longer valid", or "no such meeting").
  - The meeting's pages and WebSocket work under the `/<code>/` prefix.
- **Without a server:** the link is the computer's LAN address, the meeting checks the password and serves every page, and there is no countdown before Solin opens.

### What the hub stores per code

| Field | Notes |
|---|---|
| code | 6 characters, unique; forgotten (and reusable) only after 400 days without its owner |
| owner | sha256 of the owner secret |
| start | ISO time for the waiting page's countdown; empty for none |
| state | active, or inactive ("no longer valid"; the owner may re-activate it) |

**Not stored:** names, passwords, meeting titles or attendance.

### Hub API for Solin

- `POST /api/codes {owner, startsAt}` → a new code (rate-limited per address).
- `POST /api/codes/sync {codes: [{code, secret, startsAt, active}]}`: start times and states, sent whenever they change; codes the hub does not know as ours come back as `rejected` and get new ones.
- `GET /api/hub`: the tunnel server's port and token.
- `POST /api/turn {code, secret}`: time-limited TURN credentials for that meeting.
- Tunnel (frp): one proxy named after the code, with the code and secret in its metadata.

### From the hub's entry page to the hall

- **Ticket:** after the hub checks the password, it gives the browser a short-lived **admission ticket**.
  - It is signed with a key the hub and the congregation share, and carries the code, the name, the count and the expiry.
  - The hall accepts the ticket instead of asking for the password again, and puts the person in the lobby.
  - The ticket also carries the person into the lobby when the operator opens the meeting later.
- **Remembered devices:** moderator and stage devices that were already approved skip the password step and prove themselves to the hall directly. Moderators use the challenge signed with their device key. Stage devices use the remembered device token.

## Still open

- **The moderator device expiry:** 6 months is proposed.
- **Rate-limit values:** failed passwords per IP and per code.
- **The wording** of the share text and of every page, in en / pt / es.

## Implementation outline

**solin-hub:**
- path routing on `meet.<domain>` with a single certificate;
- the code registry (stored instead of `halls.json`'s per-hall subdomains), including issuing codes and reserving retired ones;
- password-hash check with rate limits;
- the entry, countdown, ended and invalid pages, with hub time;
- the API above;
- admission tickets.

**Solin:**
- the "Meeting links" setting;
- the schedule from the congregation's meeting days, with edits;
- reserving, renewing and retiring codes, plus the low-codes warning;
- password generation and hashing;
- automatic and early opening, with the notification;
- the hall's pages under the `/<code>/` prefix;
- the count question, the live total, and the official count at 0.75;
- the stage and moderator approval flow, badges, device keys and the device list;
- New link, and changing only the password;
- the LAN-only fallback.

**Differences from the target:**
- **Codes:** the hub issues one code at a time on Solin's request instead of `reserve`-ing batches; a link created while the server is unreachable works on this network until the server answers.
- **Password:** the hall checks it, so before Solin opens the meeting the hub's waiting page has no password field; the name, password and count come after it opens.
- **A future meeting's code while another meeting is open:** the hub sends it to the hall, whose page answers that the link is not valid now (the hub's countdown only shows while the hall is offline).
- **Low-codes warning:** with local codes it only appears when Solin has not been opened for weeks.

**Not built yet:** the password-hash check on the hub, admission tickets, and the hub-served "ended" page.
